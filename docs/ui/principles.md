# Web UI 設計原則

この文書は、`apps/web` の UI を設計・実装・レビューする際に共通して適用する横断ルールを定める。

個別画面の構造・操作・遷移・表示要素は各画面仕様で定義し、本書はそれらに共通する判断基準として扱う。

## 1. UI の役割

本 Web UI は、配信データの収集・確認・分析を効率的に行うための**作業用インターフェース**である。

マーケティングサイト、ランディングページ、プロモーションサイトとしての表現を目的としない。

そのため、見た目の演出や説明量よりも、次を優先する。

1. ユーザーが現在の状態を把握できること
2. 次に行う操作が明確であること
3. 分析対象となる情報を十分な領域で確認できること
4. 主要操作までの手数が少ないこと
5. 同種の操作・状態表現が画面間で一貫していること

## 2. 情報密度と画面領域

画面領域は、ユーザーが作業判断に必要とする情報へ優先的に割り当てる。

特に、配信・チャット・タイムライン・場所・PC 視点などの分析コンテンツが主役となる画面では、装飾要素や説明文によって主コンテンツ領域を圧迫しない。

### 原則

- 主コンテンツをファーストビュー内で把握しやすくする
- 同じ情報を複数箇所へ重複表示しない
- 操作に不要な余白や大型 Hero 領域を設けない
- 補助情報は、主情報との優先度差が分かる配置にする
- カード化は情報のまとまりを表す必要がある場合に限る

## 3. 仕様に存在しない UI を推測で追加しない

UI 実装者および AI / Codex は、仕様に記載されていない UI 要素を「分かりやすそう」「一般的だから」「見栄えがよいから」という理由で追加してはならない。

特に、以下を推測で追加しない。

- 新しい画面
- 新しい画面遷移
- CTA
- Modal / Dialog
- Step UI / Wizard
- Tab
- Card
- Sidebar
- Breadcrumb
- Tooltip
- Help panel
- Welcome message
- Tips
- Tutorial
- キャッチコピー
- サブタイトル
- decorative eyebrow text
- 機能説明目的の長文

必要性が仕様から判断できない場合は、既存 UI を最小限維持し、仕様へ判断を戻す。

## 4. テキストの原則

UI 上の文章は、ユーザーの**操作・判断・状態理解に必要なものだけ**を表示する。

文章量を増やすことで UI を分かりやすくするのではなく、情報設計・ラベル・配置・状態表現によって理解できることを優先する。

### 原則として表示してよいテキスト

- 画面タイトル
- セクション見出し
- フィールドラベル
- ボタン・リンクのラベル
- データ項目名
- ステータス
- Loading state
- Empty state
- Error state
- 成功・失敗など操作結果の通知
- 入力条件や制約など、ユーザー判断に必要な補足
- 危険操作や不可逆操作に必要な警告

### 原則として表示しないテキスト

- キャッチコピー
- ブランドメッセージ
- 「この画面では〜できます」のような恒常的な機能説明
- 操作すれば理解できる内容を文章で重ねて説明する補助文
- Welcome message
- Tips
- decorative eyebrow text
- コンテンツの意味を増やさないサブタイトル
- 空白を埋めるための文章

### 例外

説明がなければ誤操作・誤解・データ損失につながる場合は、必要最小限の補足を表示してよい。

ただし、恒常的な長文説明を配置する前に、ラベル・状態表現・レイアウトで解決できないか検討する。

## 5. 操作と画面遷移

ユーザーの主要目的に対する導線は直接的にする。

- 不要な確認画面を挟まない
- 不要な中間ページを作らない
- 主要操作を複数の UI に重複配置しない
- 一覧から対象を選択した後の遷移先は、画面遷移仕様を正本とする
- Modal にするか別画面にするかを実装者判断で変更しない

画面遷移の正本は `docs/ui/navigation.md` とする。未作成または未定義の遷移については推測で決定しない。

## 6. 状態は明示する

非同期処理やデータ取得を伴う UI は、ユーザーが現在の状態を判断できるようにする。

必要に応じて次の状態を定義する。

- Initial
- Loading
- Empty
- Ready
- Submitting / Processing
- Success
- Error
- Disabled

状態ごとの文言・操作可否・再試行可否などは個別画面仕様で定義する。

### 状態表現の原則

- Loading 中に操作可能と誤認させない
- Empty と Error を同じ表示にしない
- 処理中か停止中か分からない状態を作らない
- Error 時には、可能であれば次に取れる行動を示す
- API や内部実装の詳細をそのままユーザーへ露出しない

## 7. 情報階層を UI 装飾より優先する

情報の重要度は、意味のある構造で表現する。

優先順位は次の順とする。

1. 画面・ワークスペースの主要目的
2. 主要データ
3. 主要操作
4. 状態
5. 補助データ
6. 補助操作

Border、背景、Shadow、Card などの装飾だけで情報構造を作らない。

## 8. 一貫性を優先する

同じ意味・同じ状態・同じ操作には、可能な限り同じ表現を使う。

- 同じ操作に異なるラベルを使わない
- 同じ status に異なる見せ方を使わない
- 同じ種類の一覧で操作方法を不用意に変えない
- 既存パターンを変更する場合は、その画面だけの例外にせず、横断ルールとして妥当か確認する

## 9. アクセシビリティを壊さない

作業効率を優先する場合でも、基本的なアクセシビリティを犠牲にしない。

- 操作要素は semantic HTML を優先する
- Keyboard 操作可能な要素を独自クリック要素へ置き換えない
- Form control には識別可能な label を持たせる
- 状態や意味を色だけに依存させない
- Loading / Error など重要な状態は支援技術でも認識可能にする

個別のアクセシビリティ要件は、必要に応じて画面仕様・Acceptance Criteria・E2E で補強する。

## 10. AI / 実装者が仕様不足に遭遇した場合

仕様に不足・曖昧さ・矛盾がある場合は、次の順に扱う。

1. `docs/ui/principles.md` を確認する
2. `docs/ui/navigation.md` を確認する
3. 対象の `docs/ui/screens/*.md` を確認する
4. 既存実装・既存 E2E を参考情報として確認する
5. それでも判断できない場合は、**新しい UI を推測して追加しない**

既存実装は現状を示す参考情報であり、UI 仕様と矛盾する場合の正本ではない。

判断が必要な箇所は、仕様上の未決事項として明示し、人間へ確認する。

### 判断を止めるべき代表例

- 遷移先が複数解釈できる
- 表示すべきデータ項目が不明
- 新しい Modal / Tab / Card 等が必要か判断できない
- 説明文の必要性を仕様から判断できない
- Error / Empty 時に許可する操作が不明
- 既存実装と UI 仕様が矛盾している

## 11. 正本と優先順位

UI に関する判断が競合する場合は、原則として次の優先順位で扱う。

1. 明示された要求・Acceptance Criteria
2. `docs/ui/screens/*.md`
3. `docs/ui/navigation.md`
4. `docs/ui/principles.md`
5. 既存 E2E
6. 既存実装

既存実装や一般的な Web UI の慣習を理由に、上位仕様を上書きしてはならない。

## 12. 個別画面仕様への要求

後続の画面仕様では、本書を参照したうえで最低限以下を定義する。

- Purpose
- Entry
- Layout / Information hierarchy
- Primary actions
- Transitions
- Visible elements
- Forbidden elements
- Loading state
- Empty state
- Error state
- Acceptance Criteria

本書に記載された横断原則を各画面仕様へ重複記載する必要はない。画面固有の例外がある場合のみ、その理由と範囲を明記する。
