# YouTube Stream Analyzer — 開発マイルストーン

## 1. このドキュメントの目的

YouTube Stream Analyzerの開発順序を、利用者が実際に操作して価値を確認できる単位で定義する。

本ドキュメントにおけるマイルストーンは、技術要素や内部コンポーネントの完成を表すものではない。

> **各マイルストーンの終了時点で、単独で起動・操作・確認できる機能が完成していることを必須とする。**

プロダクト全体の到達像は[プロダクト方針とロードマップ](./product-roadmap.md)、システムの責務と採用技術は[システム全体構成](./architecture.md)を参照する。

本ドキュメントを、開発マイルストーンと完了条件の正本とする。`product-roadmap.md`に記載されている既存の実装マイルストーンより、本ドキュメントの定義を優先する。

---

## 2. マイルストーンの基本原則

### 2.1 技術要素だけをマイルストーンにしない

次のような項目は必要な開発作業ではあるが、単独ではマイルストーンとしない。

- PostgreSQLを起動する
- Go APIの雛形を作る
- Pythonワーカーを起動する
- ジョブキューを実装する
- OpenAPIを作る
- CIを構築する
- テーブルを作成する

これらは、利用者が操作できる機能を完成させるための内部タスクとして、該当するマイルストーンへ含める。

### 2.2 UI、API、保存、処理を縦断して完成させる

マイルストーンは、原則として次の流れを一つ以上含む。

```text
利用者の操作
  ↓
Web UI
  ↓
Main API
  ↓
データ保存またはバックグラウンド処理
  ↓
結果をWeb UIで確認
```

バックエンドだけ、画面だけ、データベースだけが完成した状態では、マイルストーンを完了としない。

### 2.3 前のマイルストーンだけで利用できる

各マイルストーンで完成した機能は、次のマイルストーンの実装を待たずに利用できなければならない。

例えば、チャット収集のマイルストーンは、収集したチャットを画面で閲覧できる状態まで完成させる。

### 2.4 実データで確認する

テストコードではfixtureやモックを使用してよいが、マイルストーンの完了デモでは、原則として実在するYouTube配信を使用する。

外部サービスの制約により実データで確認できない場合は、理由と未確認範囲を明記し、マイルストーンを完了扱いにしない。

### 2.5 完成していない機能を画面に出さない

後続マイルストーンのボタン、メニュー、診断情報、プレースホルダーは、利用可能になるまで通常画面へ表示しない。

未完成機能を先に並べて全体像を見せるのではなく、現在利用できる操作だけを明確に提供する。

---

## 3. 全マイルストーン共通の完了条件

各マイルストーンは、個別の完了条件に加え、次の条件をすべて満たした場合に完了とする。

- ドキュメントに記載した手順でローカル起動できる
- 利用者向けの開始地点が明確である
- 入力から結果確認までの一連の操作が完走する
- 保存したデータがアプリケーション再起動後も残る
- 処理中、完了、失敗の状態を利用者が判別できる
- 外部サービスの失敗が無言で握り潰されない
- 完了シナリオを確認するE2Eテストが1本以上ある
- 関連する単体テスト・統合テストがCIで成功する
- 次のマイルストーンの未実装機能がなくても利用できる
- 完了デモで使用した操作手順がドキュメントに残っている

マイルストーンを閉じるためだけの仮データ、固定レスポンス、手動DB更新には依存しない。

| マイルストーン | 完成時にできること | 対応する到達段階 |

## 5. M1 — 終了済み配信を登録し、配信情報を確認する

### 利用者ができること

実在する終了済みYouTube配信のURLを入力し、取得した配信情報を確認して登録できる。登録済み配信は一覧と詳細から再度確認できる。

### 操作シナリオ

1. 配信登録画面を開く
2. 終了済み配信のYouTube URLを入力する
3. タイトル、チャンネル、サムネイル、配信日時、動画時間を確認する
4. 配信を登録する
5. 配信一覧に登録した配信が表示される
6. 一覧から詳細画面を開き、保存された配信情報を確認する
7. アプリケーションを再起動しても登録内容が残っている

### 実装範囲

- React Web UIの最小構成
- Go Main APIの最小構成
- PostgreSQL接続とマイグレーション
- YouTube URLの解析と動画ID抽出
- 配信情報の取得
- 配信プレビュー
- Streamの登録、一覧、詳細取得
- 同一動画IDの重複登録防止
- 入力エラーと取得エラーの画面表示
- ローカル起動手順

### 完了条件

- 終了済み配信を実データで登録できる
- URL入力から詳細表示までUIだけで完結する
- 不正URL、存在しない動画、取得不能な動画で理由が表示される
- 同じ動画を再登録しても重複データが作成されない
- 登録一覧と詳細がリロード後も表示される

### このマイルストーンに含めないもの

- バックグラウンドジョブ
- ライブチャット取得
- 動画プレーヤー
- 解析予約

---

## 6. M2 — ライブチャットをバックグラウンド収集し、時系列で閲覧する

### 利用者ができること

登録済み配信に対してライブチャット収集を開始し、画面を閉じても継続する処理の状態を確認できる。完了後は、収集したチャットを動画内時刻順に閲覧できる。

### 操作シナリオ

1. M1で登録した配信の詳細画面を開く
2. チャット収集を開始する
3. 配信一覧または詳細画面で、現在の工程と取得件数を確認する
4. 画面をリロードしても処理が継続していることを確認する
5. 完了後、チャット一覧を開く
6. チャットを動画開始からの経過時刻順に閲覧する
7. 失敗した場合はエラー内容を確認し、再実行する

### 実装範囲

- 配信収集Pythonワーカー
- PostgreSQLジョブテーブル
- `FOR UPDATE SKIP LOCKED`によるジョブ取得
- CollectionJobとCollectionStep
- チャットリプレイ取得
- ページング
- 重複排除
- 動画開始からの経過時刻への正規化
- ChatMessage保存
- ジョブ状態、現在工程、取得件数、エラー表示
- 失敗ジョブの再実行
- チャット一覧画面

### 完了条件

- Go Main APIが登録したジョブをPythonワーカーが処理する
- HTTPリクエスト終了後も収集処理が継続する
- 数時間規模の実配信からチャットを取得できる
- 処理状態と取得件数が画面から確認できる
- 収集済みチャットを時系列で閲覧できる
- 同じジョブの再実行でチャットが重複しない
- 失敗理由を確認して再実行できる

### このマイルストーンに含めないもの

- 動画との時刻同期
- チャット内容の分析
- リアルタイムチャット取得

---

## 7. M3 — 動画とチャットを同期して場面を探す

### 利用者ができること

YouTube埋め込みプレーヤーで配信動画を再生しながら、その時刻に対応するチャットを確認できる。チャットを選択すると動画の該当時刻へ移動でき、文字列検索から場面を探せる。

このマイルストーンをPhase 1の完成とする。

### 操作シナリオ

1. 登録済み配信のデータ収集を開始する
2. メタデータとチャットの工程別進捗を確認する
3. 収集完了後、配信詳細画面を開く
4. YouTubeプレーヤーで動画を再生する
5. 再生時刻周辺のチャットを確認する
6. チャットを選択し、動画を該当時刻へ移動する
7. チャットを文字列検索する
8. 検索結果から動画の該当時刻へ移動する

### 実装範囲

- 収集工程単位の状態管理
- 一部工程失敗時の個別再実行
- YouTubeプレーヤー
- チャットの時刻同期表示
- チャットからの時刻ジャンプ
- チャットの文字列検索
- 取得件数とエラー表示

### 完了条件

- メタデータとチャットをバックグラウンド収集できる
- プレーヤーとチャットが動画開始からの経過時刻で接続される
- チャットからプレーヤーの該当時刻へ移動できる
- 検索結果から場面を再生できる
- 成功済み工程をやり直さず、失敗工程だけ再実行できる

### このマイルストーンに含めないもの

- サーバーによる動画・音声ファイルの取得、保存、解析
- 注目区間の自動判定
- 複数配信の比較
- コンテキストDB

---

## 8. M4 — 配信を事前予約し、終了後に自動収集する

### 利用者ができること

開始前または配信中のYouTube URLを登録しておくと、システムが配信状態を監視し、アーカイブとチャットリプレイが利用可能になった後に自動で収集を開始する。

### 操作シナリオ

1. 開始予定または配信中のYouTube URLを登録する
2. 予約一覧で現在の状態を確認する
3. 配信開始後、状態が配信中へ変化する
4. 配信終了後、アーカイブ準備待ちへ変化する
5. アーカイブ利用可能後、自動的に収集が開始される
6. 完了後、M3と同じ配信詳細画面で結果を閲覧する

### 実装範囲

- 解析予約登録
- 予約一覧と詳細
- 配信状態の定期確認
- 予約状態遷移
- 配信開始・終了判定
- アーカイブ利用可能判定
- チャットリプレイ利用可能判定
- 自動収集ジョブ登録
- 予約キャンセル
- 監視失敗と収集失敗の区別

### 完了条件

- 利用者が収集開始ボタンを押さなくても、終了後に収集が完了する
- `scheduled`、`monitoring`、`live`、`waiting_for_archive`、`collecting`、`completed`を画面で判別できる
- 監視処理を再起動しても予約状態を復元できる
- 同じ予約から収集ジョブが重複作成されない
- 予約をキャンセルできる
- 完了後はM3の閲覧機能をそのまま利用できる

### このマイルストーンに含めないもの

- 配信中データのリアルタイム保存
- 複数チャンネルの自動追跡
- カレンダー連携

---

## 9. M5 — 配信中のデータをリアルタイムに収集・閲覧する

### 利用者ができること

配信中の動画を登録すると、ライブチャットと時系列指標が配信中に保存され、閲覧画面へ継続的に反映される。配信終了後はアーカイブデータと照合し、同じ配信として閲覧を継続できる。

### 操作シナリオ

1. 配信中のURLを登録する
2. リアルタイム収集を開始する
3. 受信したチャットが時系列で画面へ追加される
4. 同時接続数、コメント投稿速度などの取得状況を確認する
5. 画面を閉じてもサーバー側で収集が継続する
6. 配信終了後、アーカイブ準備と補完処理を確認する
7. 完了後、M3の配信詳細画面で全データを閲覧する

### 実装範囲

- リアルタイム収集ジョブ
- ライブチャットの継続取得
- 同時接続数等の時系列イベント保存
- 配信メタデータ変化の記録
- UIへの定期反映
- 配信終了検知
- アーカイブデータとの重複排除と補完
- 切断時の再接続

### 完了条件

- 配信中に受信したデータが数分以内に画面へ反映される
- 画面を閉じても収集が継続する
- 一時的な通信失敗後に収集を再開できる
- 配信終了後も同一Streamとしてデータを閲覧できる
- アーカイブ補完後にチャットが重複しない
- リアルタイム収集の欠損・再接続履歴を確認できる

### このマイルストーンに含めないもの

- AIによるリアルタイム判定
- リアルタイム自動切り抜き
- サーバーによる配信動画・音声の取得、保存、解析

---

## 10. M6 — タイムラインから注目区間を探索し、候補として保存する

### 利用者ができること

収集済み配信の時間軸上で、コメント量、ユニーク投稿者数、スーパーチャット、特定語句などを確認し、気になる区間へ移動できる。利用者自身が区間を切り抜き候補として保存できる。

### 操作シナリオ

1. 収集済み配信のタイムラインを開く
2. コメント量などの時系列変化を確認する
3. 山や特定語句の位置を選択する
4. プレーヤーを該当時刻へ移動する
5. 前後のチャットを確認する
6. 開始時刻・終了時刻を指定して候補として保存する
7. 候補へメモと状態を設定する
8. 保存済み候補一覧から再度該当区間を開く

### 実装範囲

- 時間窓単位のチャット集計
- ユニーク投稿者数集計
- スーパーチャット集計
- 特定語句位置
- タイムライン表示
- タイムラインからの時刻ジャンプ
- 区間選択
- ユーザーマーカー
- ClipCandidateの手動登録
- 候補メモと状態管理

### 完了条件

- 長時間配信の全体傾向を一画面で確認できる
- タイムラインの任意位置から動画とチャットへ移動できる
- 開始・終了時刻を持つ候補を保存できる
- 候補へメモと状態を設定できる
- 保存した候補を一覧・詳細から再確認できる
- この段階ではAIがなくても、実際の素材探索に利用できる

### このマイルストーンに含めないもの

- 高度な盛り上がり判定
- 自動候補採用
- 複数視点の比較
- 文脈による候補理由生成

## 11. M7 — 同じ出来事の複数配信視点を行き来して比較する

### 利用者ができること

同じイベントや企画に参加した複数配信をグループ化し、同じ実時刻に対応する各配信の映像とチャットを行き来して比較できる。

### 操作シナリオ

1. 同じイベントに属する複数配信をグループへ追加する
2. 各配信の開始日時と時刻対応を確認する
3. 1つの配信で気になる区間を開く
4. 同じ実時刻に配信していた別配信を表示する
5. 別視点の動画とチャットを確認する
6. 関連する別視点区間を候補へ紐付ける

### 実装範囲

- イベントまたは配信グループ
- 配信開始日時による共通時刻軸
- 複数配信の時刻対応
- 同時刻に存在する別配信の検索
- 配信間ジャンプ
- 複数視点比較UI
- 候補と関連区間の紐付け
- 手動による時刻補正

### 完了条件

- 2本以上の配信を同じグループとして管理できる
- 片方の配信時刻から、同じ実時刻の別配信へ移動できる
- 配信開始時刻のずれを補正できる
- 別視点のチャットを比較できる
- 1つの候補へ複数の関連区間を保存できる
- 複数配信を往復する素材確認作業に実利用できる

### このマイルストーンに含めないもの

- 内容理解による自動視点対応
- 発話者識別
- 同一シーンの映像認識
- 自動マルチカメラ編集

---

## 12. M8 — 文脈を登録し、配信区間へ関連付ける

### 利用者ができること

配信者、グループ、イベント、出来事、ミーム、人物関係を手動で登録し、出典とともに管理できる。登録した文脈を配信または特定区間へ関連付け、配信詳細から確認できる。

コンテキストDBのデータモデルは、まず手動入力で利用価値を確認する。自動収集を先に実装しない。

### 操作シナリオ

1. 配信者を人物として登録する
2. イベントまたはミームを登録する
3. 人物同士、人物とイベントの関係を登録する
4. 情報源URLと根拠を登録する
5. 配信の特定区間へ文脈を関連付ける
6. 配信詳細画面で関連する人物・出来事・ミームを確認する
7. 文脈の内容や有効期間を修正する

### 実装範囲

- ContextEntity
- ContextAlias
- ContextRelation
- ContextEvent
- SourceDocument
- Evidence
- 有効期間
- 確認状態
- コンテキストCRUD画面
- 配信・区間との関連付け
- 配信詳細での関連コンテキスト表示

### 完了条件

- 人物、イベント、出来事、ミームを登録・編集できる
- 別名や表記揺れを管理できる
- 出典と根拠を必須情報として保存できる
- 時間によって変化する関係を有効期間付きで保存できる
- 配信または区間へ文脈を関連付けられる
- 登録した文脈が素材確認時に役立つ形で表示される

### このマイルストーンに含めないもの

- Webからの自動収集
- LLMによる自動抽出
- Embedding検索
- 自動的な文脈関連付け

---

## 13. M9 — 周辺情報を自動収集し、事実候補を確認・承認する

### 利用者ができること

配信者またはイベントを指定して周辺情報収集を実行し、取得元、抽出された事実候補、根拠箇所を確認できる。候補を承認するとM8の確定コンテキストへ反映される。

### 操作シナリオ

1. 登録済みの配信者またはイベントを開く
2. コンテキスト収集を開始する
3. 収集状態と情報源件数を確認する
4. 抽出されたClaim候補を一覧で確認する
5. 情報源と根拠箇所を開く
6. 候補を承認、修正、却下する
7. 承認済み内容が人物関係や出来事へ反映される
8. 同じ情報源を再収集しても重複しない

### 実装範囲

- コンテキスト収集Pythonワーカー
- YouTubeチャンネル・動画情報収集
- Webページ取得と本文抽出
- SourceSnapshot保存
- LLMによる構造化抽出
- ClaimとClaimEvidence
- Entity Resolution
- Claim確認・承認UI
- 承認内容の確定コンテキスト反映
- Embedding生成と類似候補検索

### 完了条件

- UIから収集ジョブを開始できる
- 収集した情報源とスナップショットを確認できる
- LLMの抽出結果が確定データへ直接登録されない
- 各Claimに根拠箇所と情報源が保存される
- 承認、修正、却下ができる
- 承認結果がM8の画面へ反映される
- 再収集時の重複と更新を区別できる

### このマイルストーンに含めないもの

- 人間の確認を経ない自動確定
- 情報源の正しさの完全自動判定
- 切り抜き候補の自動生成

## 14. M10 — 文脈と複数視点を踏まえた切り抜き候補を確認・管理する

### 利用者ができること

配信の時系列指標、チャット、複数視点、登録済みコンテキストを組み合わせて生成された切り抜き候補を確認できる。候補理由と根拠を見ながら採否を判断し、制作状態を管理できる。

### 操作シナリオ

1. 収集済みの配信またはイベントを開く
2. 候補抽出を実行する
3. 候補一覧をスコアや時刻順で確認する
4. 候補区間の動画と前後チャットを確認する
5. 関連する別視点へ移動する
6. 関係する過去の出来事やミームを確認する
7. システムが提示した候補理由と根拠を確認する
8. 候補を採用、不採用、確認中などに変更する
9. 採用候補へメモと関連素材を保存する

### 実装範囲

- 分析ワーカー
- 時系列指標による候補区間生成
- チャットを用いた区間要約
- 関連別視点の候補提示
- コンテキストとの関連付け
- 候補理由と根拠の保存
- 候補スコア
- 候補一覧・詳細UI
- 候補状態管理
- 制作メモと関連素材管理

### 完了条件

- 実配信から候補区間を生成できる
- 各候補に開始・終了時刻がある
- 候補理由だけでなく、判断に使ったデータと根拠を確認できる
- 関連する別視点とコンテキストを辿れる
- 利用者が候補の採否を変更できる
- 採用後の制作状態を管理できる
- 候補を鵜呑みにせず、人間が確認・判断する流れになっている

### このマイルストーンに含めないもの

- 動画の自動編集
- 自動投稿
- 人間の確認を経ない全自動切り抜き生成

## 16. GitHub上での管理方針

各開発マイルストーンは、GitHub Milestoneとして管理する。

Issueはコンポーネント単位ではなく、マイルストーンの完成条件へ結び付ける。

例えばM2では、次のIssueが存在してもよい。

- Go APIからチャット収集ジョブを登録する
- Pythonワーカーがジョブを排他取得する
- チャットを保存する
- 進捗を画面へ表示する
- 収集結果を時系列表示する
- 完了シナリオのE2Eテストを追加する

ただし、「ワーカーが起動した」「テーブルが作成された」だけではM2を完了としない。すべてのIssueが、最終的に利用者の操作シナリオへ接続されている必要がある。

### マイルストーンを閉じる前の確認

1. 操作シナリオを実データで実行する
2. 完了条件を一項目ずつ確認する
3. E2EテストとCI結果を確認する
4. 未完成機能が通常画面へ露出していないことを確認する
5. 既知の制約をドキュメントへ記録する
6. 次のマイルストーンがなくても利用できることを確認する

## 17. 現時点の実装開始点

最初に着手するのはM1とする。

M1では、モノレポ全体の空構成を先に作り切るのではなく、終了済み配信を登録して一覧・詳細で確認するために必要な範囲だけを実装する。

M1に不要なPythonワーカー、コンテキストDB、pgvector、分析機能は導入しない。

後続技術は、それを必要とする最初のマイルストーンで追加する。

これにより、全体構成を維持しながらも、利用価値のない基盤実装だけが先行することを防ぐ。

## 18. M2〜M4実データ取得補完ワークストリーム

M2〜M4の機能実装とfixtureによるE2Eは完了しているが、実際のYouTubeからチャットリプレイを取得する本番用Gatewayサービスの実データ確認が必要である。

この不足は新しいプロダクトマイルストーンとして扱わず、M2、M3、M4の完了条件を満たすための内部ワークストリームとして扱う。

### 到達状態

```text
Web UI
  ↓
Main API ── PostgreSQL
               ↑
配信収集Worker
  ↓ private HTTP
youtube-data-gateway
  └─ chat replay
        ↓
      YouTube
```

実在する配信からGateway経由でチャットを保存し、M3の同期閲覧・検索・時刻ジャンプ、M4の終了後自動収集まで完走できる。

### 実装順序

```text
#87 Gateway責務・API・認証・エラー契約
  └→ #88 実チャットリプレイ取得 → #90 Gateway統合E2E・Railwayデプロイ → #76 実配信完了デモ
```

### M2完了条件への追加

- 実YouTubeチャットリプレイをGateway経由で取得できる
- 数時間規模の実配信でチャット保存・重複排除・再実行を確認できる

### M3完了条件への追加

- 実配信でチャットの同期表示、検索、時刻ジャンプを確認できる

### M4完了条件への追加

- Railway検証環境でWorkerとGatewayを継続稼働できる
- 実配信の終了後、手動収集操作なしで実チャット収集まで完了する
- WorkerまたはGateway再起動後も状態・ジョブを復元できる
- `m4-demo-report`がPASSになる

- 親計画: Issue #86
