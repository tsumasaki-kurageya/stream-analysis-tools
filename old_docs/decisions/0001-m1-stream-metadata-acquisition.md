# ADR-0001: M1の配信メタデータ取得責務

- Status: Accepted
- Date: 2026-08-01
- Related milestone: M1
- Related issue: #13

## Context

M1では、利用者が終了済みYouTube配信のURLを入力し、メタデータを確認して登録する。システム全体構成では収集処理をPythonワーカーへ分離するが、M1ではバックグラウンドジョブを導入しない。

プレビューは利用者操作に対して即時応答する必要があり、取得対象はYouTube Data API `videos.list` で得られる軽量なメタデータに限られる。

## Decision

M1のプレビューおよび登録時のメタデータ取得は、Main APIが利用者のHTTP要求内で同期実行する。

- Main APIはURL解析、YouTube Data API呼び出し、終了済みライブ配信判定、エラー分類を担当する
- プレビュー結果は保存しない
- 登録時は元URLからメタデータを再取得し、クライアントのプレビュー値を正本にしない
- プレビュー時と登録時の2回の `videos.list` 呼び出しを許容する
- M2以降のチャット、字幕、生データ等の長時間収集はPythonワーカーが担当する
- サムネイルはYouTube URLのみ保存し、M1ではBlobへ複製しない

## Consequences

### Positive

- M1だけで利用者の登録フローを完結できる
- ジョブ基盤を先取りせず、M1の対象範囲を保てる
- 登録時の再取得により改ざん・陳腐化したプレビュー値を保存しない
- 外部APIエラーをMain APIの安定した契約へ変換できる

### Negative and trade-offs

- プレビューと登録でYouTube APIを2回呼び出す
- Main APIが限定的な外部データ取得責務を持つ
- YouTube APIの応答時間がプレビュー・登録のHTTP応答時間へ影響する

## Alternatives considered

### M1からPythonワーカーへ委譲する

ジョブ状態、ポーリング、再試行等が必要となり、M1の利用者価値に対して基盤が過剰になるため採用しない。

### プレビュー結果をそのまま登録する

クライアント値を信頼することになり、改ざんやプレビュー後の状態変化を保存する可能性があるため採用しない。

### yt-dlpを主経路とする

M1で必要な契約、タイムアウト、エラー分類を明確にしにくいため採用しない。
